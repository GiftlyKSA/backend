# Prompt for the Giftly mobile UI agent — order history and profile update

Work in the Giftly mobile repository. Read its instructions and existing API client first. Keep the current visual design, make the smallest integration changes, and use the backend's implemented contracts below. The source of truth is `../backend/docs/mobile-openapi.json` plus `../backend/docs/MOBILE-API-INTEGRATION.md`. Do not invent unsupported endpoints or use admin routes. Preserve bearer tokens securely and use the current API base URL.

All UUID examples are illustrative. JSON strings, numbers, booleans, nulls, and arrays must retain their wire types. Send `Authorization: Bearer <access_token>` on all endpoints below except `GET /api/cities`. A domain error is usually `{"error":{"code":"NOT_FOUND","message":"...","request_id":"..."}}`; request validation can be HTTP 422 `{"detail":[...]}`. Handle 401 by refreshing once through the existing token flow, 403 as forbidden, 404 as missing or inaccessible, and 429 using `Retry-After`.

## Reopen chat from any assigned order

1. On an old or active order detail screen, use its `id` as `order_id` in `GET /api/orders/{order_id}/conversation`. This is available to the authenticated customer or assigned courier, including after the order is completed. It has **no request body** and no pagination query. Path `order_id` is a UUID string such as `"8c420d84-9679-4330-9c5c-20de23636a6f"`. HTTP 200 response fields are all UUID strings:

   ```json
   {"conversation_id":"4e2b0465-d07e-418c-a271-b92ac5b3a7d4","order_id":"8c420d84-9679-4330-9c5c-20de23636a6f","other_user_id":"44baa8db-6c53-4f6f-bf8c-f29f93092a79"}
   ```

   A missing or unassigned order, or one belonging to someone else, returns 404. Use `conversation_id` for all history, send, read, and WebSocket calls; it is **not** interchangeable with `order_id`. Use `other_user_id` only to request the safe participant profile if needed.

2. Fetch persisted history with `GET /api/conversations/{conversation_id}/messages?limit=30`. Only the customer and courier in that conversation can use it. It has **no request body**. `conversation_id` is a UUID string path value. Optional `limit` is an integer from **1 to 100**, default **30**. Optional `cursor` is a UUID string copied unchanged from the preceding response's `next_cursor`. The first request omits `cursor`. Example first response:

   ```json
   {"items":[{"id":"2ef675ce-897e-4f06-8c92-36b8a71515b0","conversation_id":"4e2b0465-d07e-418c-a271-b92ac5b3a7d4","sender_id":"44baa8db-6c53-4f6f-bf8c-f29f93092a79","message_type":"TEXT","content":"I am on my way","is_read":false,"created_at":"2026-09-30T10:45:00+00:00"}],"next_cursor":"2ef675ce-897e-4f06-8c92-36b8a71515b0"}
   ```

   `items` is an array of messages ordered **newest first**. Each `id`, `conversation_id`, and `sender_id` is a UUID string. `message_type` is one of `TEXT`, `IMAGE`, `VIDEO`, `SYSTEM`, or `MIXED`; the current text composer only sends `TEXT`. `content` is a decrypted string, `is_read` is boolean, and `created_at` is an ISO 8601 timestamp with timezone. `next_cursor` is a UUID string or `null`. To load older messages, call the same endpoint with `cursor=<next_cursor>` until it is `null`. Do not use page numbers or offsets. A nonexistent cursor or one from another conversation returns 404; discard it and restart at the first page only after telling the user or refreshing state. Display messages chronologically by reversing each fetched page for display while preserving correct merge order. Deduplicate by message `id`.

3. For the inbox, `GET /api/conversations?limit=20` returns only the caller's conversations, newest activity first. Optional `limit` is integer 1–100, default 20. Optional `cursor` is an **opaque string** from `next_cursor`; pass it unchanged and URL-encode it. No request body. Example row: `{"conversation_id":"4e2b0465-d07e-418c-a271-b92ac5b3a7d4","order_id":"8c420d84-9679-4330-9c5c-20de23636a6f","other_user_id":"44baa8db-6c53-4f6f-bf8c-f29f93092a79","last_message_preview":"I am on my way","unread_count":1,"last_message_timestamp":"2026-09-30T10:45:00+00:00"}`. The envelope is `{"items":[...],"next_cursor":null}`. `last_message_preview` can be `null`; `unread_count` is a nonnegative integer. The direct order lookup in step 1 avoids scanning every inbox page for an old order.

4. When a thread is visibly open, call `POST /api/conversations/{conversation_id}/read` with no JSON body. It returns HTTP **204 with no response body**. Refresh unread badges from the inbox when useful. To send text without a socket, call `POST /api/conversations/{conversation_id}/messages` with JSON `{"text":"I am on my way"}`. `text` is a nonempty string of at most **4,000 characters**. HTTP 201 returns one message in the same shape as a history item. Use returned `id` to avoid duplicating its matching socket event.

5. While the chat screen needs live events, connect `WS /api/ws/conversations/{conversation_id}?token=<access JWT>`. Both the JWT and conversation membership are required. Send JSON frames `{"text":"I am on my way"}`; receive persisted message-shaped JSON events. The WebSocket is for live delivery, **not durable history**. On reconnect, token refresh, app resume, or returning to an old order, fetch the REST history again and merge by message `id`. Close the socket on logout or when leaving the live chat. Use TLS (`wss`) in production and do not log the token-bearing URL.

## Other changed profile, city, order, and rating contracts

- `GET /api/users/me` and `PATCH /api/users/me` return a generic user's `public_identifier` as an **integer** from **1000000 to 9999999**, for example `5473842`. The internal `id` remains a UUID string for path and relationship API calls. The public number is generated by the backend, unique, and read-only; never send it in PATCH or use it as a UUID. Customer responses have no user-level `rating`, `rating_count`, or avatar storage key. A courier response has `courier_profile` with courier-specific `rating` (decimal string) and `rating_count` (integer), derived from customer reviews. A customer has `courier_profile: null`. Display the public number if the profile design needs a friendly user identifier.

  Example customer `GET /api/users/me` HTTP 200 response (no request body):

  ```json
  {"id":"8c420d84-9679-4330-9c5c-20de23636a6f","public_identifier":5473842,"phone":"+966501234567","role":"CUSTOMER","status":"ACTIVE","full_name":"Sara Ahmed","email":null,"courier_profile":null}
  ```

  The `role` value is one of `CUSTOMER`, `COURIER`, or `ADMIN`; `status` is one of `ACTIVE`, `BANNED`, `PENDING_VERIFICATION`, or `REJECTED`. `full_name` and `email` may be null. For a courier, `courier_profile` is an object with `city_of_residence` string, `city_of_residence_id` UUID string, `bio` string or null, `verification_status` string, `rejection_reason` string or null, `avatar_url` null, `rating` decimal string such as `"4.50"`, and `rating_count` integer such as `12`.
- `GET /api/users/{user_id}/participant` returns a safe participant profile only when the caller shares an order or conversation with the target. It includes UUID `id`, integer `public_identifier`, `display_name` string, `role` string, and `initials` string. Courier ratings and courier details appear only for courier profiles; customer ratings are absent. Do not expect phone, email, or identity documents here.
- `GET /api/cities` requires no authentication and returns active choices with `id` (UUID string), `name` (English string), `name_ar` (Arabic string), and `shortcut` (string). Example: `{"id":"1b055c47-c3e3-48b8-aa0f-1a5052dc753b","name":"Riyadh","name_ar":"الرياض","shortcut":"RUH"}`. Display `name_ar` in Arabic UI and `name` in English UI, but submit the `id` as the existing city UUID relationship. Do not hard-code seed UUIDs.
- Orders no longer collect precise delivery locations or address notes. Remove location inputs and Open Maps actions from the UI. Keep city selection, delivery date, description, and request photos. Order totals remain computed by the backend.
- `POST /api/orders/{order_id}/ratings` is **customer-only** after the order reaches status `COMPLETED` (the backend's completed/done state). JSON request: `{"score":5,"comment":"Careful delivery"}`. `score` is an integer **1–5**; `comment` is optional string or null, max **500 characters**. The server derives the assigned courier from the order; do not send a `rated_user_id`. HTTP 201 response: `{"id":"6364a845-6a3c-4c5b-a25f-df40f8ebdfc5","order_id":"8c420d84-9679-4330-9c5c-20de23636a6f","rated_user_id":"44baa8db-6c53-4f6f-bf8c-f29f93092a79","score":5,"comment":"Careful delivery"}`. Hide the rating action for couriers, before completion, and when `current_actor_has_rated` is true. `GET /api/users/{courier_user_id}/ratings/summary` returns `{"user_id":"44baa8db-6c53-4f6f-bf8c-f29f93092a79","average_score":"5.00","count":1}`; average is a decimal string and count is integer. It represents customer-to-courier reviews only.

Update typed API models and affected screens, including historical order detail, chat inbox/thread, profile, city selectors, order creation/detail, and the post-completion customer rating action. Add focused tests for pagination, token/reconnect behavior, missing map URLs, customer-only ratings, and the public identifier type. Report which screens changed and any unsupported UI actions left pending. Do not claim the WebSocket replays history or that production payment processing is enabled.
