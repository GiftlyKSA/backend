# Giftly backend code review — 2026-09-30

This review covers the current backend, including HTTP/WebSocket authentication, admin CRUD, audit logging, orders, chat, finance, media, workers, migrations, API contracts, and query paths. It follows [AGENTS.md](../AGENTS.md) and uses the [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x00-header/) as one security checklist. Scores are engineering priority out of 10, **not CVSS**: High = 8–10, Medium = 4–7, Low = 1–3. `New` means first recorded in this review; `Carried` means the prior [review](2026-09-17-backend-review.md) already identified it. Source confirmation does not prove remote exploitability.

This is a source and offline-test review, not a line-by-line security proof. No Docker, PostgreSQL, Redis, production deployment, external vendor, or representative load test was run. Findings that depend on those environments are marked **UNCONFIRMED**. The requested unrestricted authenticated admin CRUD is treated as an intentional capability, but its consequences remain findings.

## Security

### High

**SEC-16 — Financial maintenance bypass — 9/10, carried, confirmed intentional capability.** Evidence: `app/admin/table_router.py:145-163`, `app/services/admin_table_service.py:81-160`, `app/repositories/admin_table_repository.py:155-181`, `app/migrations/versions/0002_schema_guards.py:18-86`. Generic authenticated admin table CRUD authorizes maintenance writes that bypass normal financial and issued-invoice guards. **Impact:** an erroneous or compromised administrator can make wallet, ledger, or invoice records inconsistent without the business service invariants. **Why fix:** authentication and audit do not enforce financial correctness. **Minimal fix:** keep the user-requested CRUD capability, but gate financial maintenance behind a separately authorized, expiring repair grant with reason and independent approval; reconcile touched accounts. **System impact:** routine admin edits stay available, while sensitive repairs gain a stronger boundary. **Verify:** PostgreSQL tests for denied/approved/expired grants and ledger reconciliation.

**SEC-17 — Database audit history is editable through generic admin CRUD — 9/10, new, confirmed.** Evidence: `app/models/tables.py:1192-1218` describes `AuditLog` as append-only; `app/repositories/admin_read_repository.py:113-116` lists every table as editable; `app/repositories/admin_table_repository.py:35-39` resolves any application table; `app/admin/table_router.py:145-163` exposes update/delete. The schema guards in `app/migrations/versions/0002_schema_guards.py` do not protect `audit_logs`. **Impact:** a privileged or stolen admin session can alter or remove database evidence of user, system, or admin activity. Committed events are also emitted to an application log, but independent shipping and retention are unverified. **Why fix:** an audit trail must remain trustworthy under the administrator threat model. **Minimal fix:** write audit events to an independently retained append-only destination; if product policy permits, block generic update/delete of audit rows or require a separately logged break-glass process. **System impact:** stronger forensic integrity; audit browsing remains available. **Verify:** mutation-denial and log-collector receipt/tamper tests on disposable infrastructure.

**SEC-13 — The request-size guard does not count actual body bytes — 8/10, carried, confirmed.** Evidence: `app/main.py:263-306` checks only `Content-Length`, accepts malformed values as zero, and rejects only explicitly chunked undeclared bodies. **Impact:** an upstream component that passes missing, malformed, or understated lengths can deliver a body larger than the configured cap and exhaust parser or worker memory. Actual PaaS exposure is unverified. **Why fix:** a header is not an enforcement boundary. **Minimal fix:** bound cumulative bytes in an ASGI receive wrapper, retaining the early header check. **System impact:** predictable memory use with small per-chunk overhead. **Verify:** exact-limit, oversized, absent, malformed, understated, and streamed-body cases in process and through ingress.

### Medium

**SEC-14 — General HTTP throttling fails open on Redis errors — 7/10, carried, confirmed.** Evidence: `app/core/ratelimit.py:83-99`, `app/main.py:310-355`. The ordinary limiter returns `allowed=True` after any Redis error; OTP, admin, and WebSocket controls have separate paths and are not claimed to share this failure. **Impact:** broad API abuse protection disappears during Redis failure. **Why fix:** a shared dependency outage should have an explicit security/availability policy. **Minimal fix:** fail closed for sensitive routes and define a bounded fallback or 503 for the rest, with clear health signaling. **System impact:** stronger outage behavior with a deliberate availability tradeoff. **Verify:** Redis timeout/unavailable tests across route classes and a multi-instance outage drill.

**SEC-15 — WebSocket token in a query string — 5/10, carried, UNCONFIRMED at ingress.** Evidence: `app/routers/chat.py:415-430`. A bearer token in `?token=` can be included in upstream request-URL logs even if application logs redact credentials. **Impact:** leaked URLs expose tokens until expiry or revocation. **Why fix:** URL logging outside the application is common and hard to control from route code. **Minimal fix:** use a short-lived single-use socket ticket or a supported authorization subprotocol, and redact query strings at ingress. **System impact:** a client handshake change and less credential exposure. **Verify:** inspect actual ingress/APM logs and test ticket expiry/replay if introduced.

## Reliability, correctness, and deployment

### Medium

**REL-10 — Chat delivery side effects run after the message commit — 7/10, new, confirmed.** Evidence: `app/routers/chat.py:170-193,374-395`, `app/services/notification_service.py:31-48`, `app/services/chat_service.py:148-150`. REST and WebSocket paths commit a message, then query recipient devices, attempt push, and publish to Redis. Push-provider failures are swallowed, but device lookup or Redis publish can fail after commit. **Impact:** a client can receive an error or socket closure for a message that actually persisted; retrying may create a duplicate, and participants may miss the live event until history is fetched. **Why fix:** durable writes and delivery acknowledgments need a consistent contract. **Minimal fix:** give sends a client idempotency key and enqueue a durable post-commit event/outbox; at minimum make nonessential delivery failure explicit and preserve a successful persisted-message response. **System impact:** safer retries and recoverable event delivery with a small storage/worker cost. **Verify:** failing Redis/device lookup after commit, retry deduplication, and history reconciliation tests.

**REL-09 — New device tokens can be skipped by an in-progress courier push sweep — 6/10, carried, confirmed risk.** Evidence: `app/repositories/order_notification_repository.py:77-97`, `app/services/order_notification_service.py:28-69`. Paging by random UUID `DeviceToken.id > cursor` gives no insertion-order guarantee. **Impact:** token replacement/insertion during a multi-page send can miss a courier, while provider success followed by a failed cursor stamp can repeat a page. **Why fix:** delivery coverage should be deterministic under concurrent changes. **Minimal fix:** snapshot eligible recipients per outbox item or use an insertion-ordered key and high-water mark. **System impact:** more stable coverage at modest schema/storage cost. **Verify:** concurrent registration/revocation, multipage sending, and lease-expiry tests on PostgreSQL.

**REL-11 — Request auditing is best effort after the handler — 6/10, new, confirmed.** Evidence: `app/main.py:210-260` runs `_record_http_audit` in a separate transaction after the response is produced and catches/logs write errors. A crash between the business commit and this transaction also loses the request row. **Impact:** a successful operation may have no corresponding HTTP audit record; a 500 audit event may not explain which business writes committed. **Why fix:** the user's requested complete activity history needs a defined delivery guarantee. **Minimal fix:** put critical state-change events in the same transaction as the business change, then forward them through a durable outbox; keep request metadata logging as supplementary. **System impact:** reliable critical-action traceability, with an extra durable event path. **Verify:** audit database failure and process-interruption tests around a committed action.

**DEP-01 — Migration execution is duplicated in the Compose deployment path — 5/10, new, confirmed in configuration.** Evidence: `docker-compose.yaml:64-123` runs a dedicated `migrate` service and makes API/worker/scheduler depend on it; `app/entrypoint.py:12-34` upgrades the database again before each of those commands. Alembic serializes concurrent upgrades, but extra startup work remains. **Impact:** deploys can spend longer waiting on migrations or fail service startup during transient database contention. This may relate to the earlier PaaS startup complaint but is not proven to be its cause. **Why fix:** one migration owner gives predictable startup ordering. **Minimal fix:** use the one-shot migration job for Compose and bypass the entrypoint upgrade there; for PaaS, run one release-phase migration with an explicit failure gate, then start all workers. **System impact:** faster, simpler startup while retaining fail-fast schema checks. **Verify:** deployment dry run with three workers and simulated migration failure; no Docker was run here.

**API-01 — Unknown pagination anchors restart from the first page — 5/10, new, confirmed.** Evidence: `app/repositories/order_repository.py:226-236`, `app/repositories/wallet_repository.py:129-157`. When `before_id` does not exist, the anchor condition is omitted. **Impact:** deleted/stale cursor IDs produce duplicate first-page results or a client pagination loop; wallet anchors from another wallet are also accepted as timestamps. **Why fix:** pagination needs stable, explicit invalid-cursor behavior. **Minimal fix:** reject absent or out-of-scope anchors with the established client-error envelope, or move to a validated cursor carrying sort keys. **System impact:** clients can recover predictably rather than silently repeating data. **Verify:** deleted, foreign, malformed, and valid cursors on both endpoints.

## Performance, SQL, and scalability

### Medium

**PERF-08 — Media operations hold transactions across S3 calls — 7/10, carried, confirmed.** Evidence: `app/services/media_service.py:43-119`, `app/repositories/media_repository.py:105-126`, `app/core/db.py:63-76`. Grant issuance can await presigning after acquiring an owner lock; confirm/claim can await S3 metadata and byte inspection in an open request transaction. **Impact:** storage latency holds connections, snapshots, and sometimes row locks, raising tail latency and reducing throughput. **Why fix:** network waits should not extend database critical sections. **Minimal fix:** do presigning before a short quota transaction; inspect uploaded objects outside the claim transaction and atomically recheck ownership/status/metadata before claiming. **System impact:** shorter transactions without weakening quota or one-time-use rules. **Verify:** delayed/failing S3 fake and two-session PostgreSQL race tests.

**PERF-09 — Per-request audit write and unbounded retention path — 6/10, new, confirmed growth risk.** Evidence: `app/main.py:210-260` starts a second session and insert for nearly every business/admin HTTP request; `app/models/tables.py:1192-1218` indexes audit history. No retention, archive, or partition job was found in `app/workers/` or migrations. **Impact:** added latency and database pool demand on hot paths, plus growing table/index storage and maintenance cost. Actual load impact is unmeasured. **Why fix:** mandatory auditability needs an operating lifecycle. **Minimal fix:** define retention/legal requirements, partition or archive old records to an immutable store, and measure write latency; preserve full critical-event coverage. **System impact:** bounded hot-table growth and predictable capacity without discarding security evidence. **Verify:** representative request load, audit write latency, table/index growth, and archive restore tests.

### Low / unverified

**SQL-01 — Query plans under representative data remain unknown — 3/10, carried, UNCONFIRMED.** Evidence: `app/repositories/order_repository.py:173-236`, `app/repositories/chat_repository.py`, `app/repositories/wallet_repository.py:158-205`. Order radar/inbox sorting and reconciliation aggregates may become expensive as data grows; no missing-index or N+1 incident was demonstrated. **Impact:** possible future latency and database load. **Why fix:** query and index changes should respond to measured plans, not guesses. **Minimal fix:** collect query counts and `EXPLAIN (ANALYZE, BUFFERS)` on disposable representative PostgreSQL data, then add only justified indexes or batch changes. **System impact:** targeted optimization without needless write/storage cost. **Verify:** plans, query counts, and p95 latency before and after any change.

## Data model and requested API contracts

### Medium

**DATA-01 — Requested generic user fields and deletion lifecycle are absent — 6/10, new, confirmed requirement gap.** Evidence: `app/models/tables.py:111-143`, `app/models/enums.py:20-25`. The current `users` table has no `gender` or deletion-reason field, and `UserStatus` has no `DELETED` value, despite the previously requested user design. `deleted_at` exists, but it does not supply the requested status and reason. **Impact:** admin/API cannot represent the requested profile or explain deletion using the requested contract. **Why fix:** client and operational workflows need a consistent lifecycle. **Minimal fix:** agree the final public contract, add fields through a reviewed Alembic migration, update schemas/admin forms, and test old rows/defaults. **System impact:** additive schema/API work with data-backfill and client compatibility considerations. **Verify:** migration upgrade/downgrade and create/update/delete API/admin round trips.

**DATA-02 — Courier identity collection and duplicate detection remain after removal request — 6/10, new, confirmed requirement gap.** Evidence: `app/admin/templates/courier_new.html:12`, `app/models/tables.py:149-195`, `app/services/auth_service.py:195-228`, `app/core/identity.py:7-21`. The new-courier form still requires an identity document; encrypted identity fields, an HMAC fingerprint, a uniqueness index, and duplicate-check logic remain. **Impact:** the backend still collects and retains identity data the user asked to remove, increases sensitive-data handling, and can reject registrations on the old duplicate rule. **Why fix:** reduce unnecessary PII and align behavior with the current product requirement. **Minimal fix:** remove document collection, fingerprinting, duplicate checks, constraints, and stored columns in one reviewed migration; update registration/admin contracts. **System impact:** less sensitive data and a changed courier onboarding requirement. **Verify:** registration/admin flows and migration on disposable PostgreSQL, including preexisting rows.

## Code quality, clean code, and maintainability

### Medium

**QUAL-01 — Admin user detail still references removed rating fields — 4/10, new, confirmed.** Evidence: `app/admin/templates/user_detail.html:12` renders `user.rating` and `user.rating_count`; `app/models/tables.py:111-143` has neither. **Impact:** the page shows blank/undefined values and suggests customers carry courier ratings. **Why fix:** misleading admin output makes support decisions harder. **Minimal fix:** remove that row for generic users, or render an explicitly loaded courier-only rating aggregate. **System impact:** correct display without changing stored data. **Verify:** render the detail page for customer and courier accounts.

### Low

**CLEAN-01 — OTP service documentation has an obsolete lifetime — 2/10, new, confirmed.** Evidence: `app/services/otp_service.py:70-76` describes a 180-second code, while `app/core/config.py:136` sets `OTP_TTL_SECONDS = 60`. **Impact:** maintainers may implement client timing or tests from the wrong value. **Why fix:** security-sensitive timing documentation should match the configured default. **Minimal fix:** refer to the configured TTL instead of a hard-coded number. **System impact:** clearer maintenance with no runtime change. **Verify:** inspect service documentation and OTP expiry test.

## Enhancement and client experience

### Medium

**ENH-01 — No participant-scoped order event stream — 5/10, new, confirmed limitation.** Evidence: `app/routers/chat.py:207-219` exposes a chat WebSocket; `app/routers/orders.py:218-233` handles order acceptance; `app/workers/order_notifications.py:14-18` periodically pushes new-order alerts. There is no order-status WebSocket or equivalent live subscription in the current route inventory. **Impact:** couriers must fetch available orders after a generic push, and customers must refresh/poll to see acceptance and later status changes. **Why fix:** the UI cannot give immediate, reliable order-state feedback from the current live API. **Minimal fix:** define committed, participant-authorized order events with a last-seen cursor and GET reconciliation; document polling until implemented. **System impact:** a new client contract, Redis/event delivery capacity, and authorization tests. **Verify:** multi-device/multi-worker delivery, reconnect, missed-event recovery, and forbidden subscriptions.

## Intentional limitations and external verification

- **Production payments:** Dhamen scaffolding is not a proven live payment integration; production payment disablement is intentional. Do not infer readiness from API shape or fakes.
- **SMS/email/push vendors:** real credentials, payloads, timeouts, and receipts were not exercised. The earlier `INT-01` vendor-contract risk remains **UNCONFIRMED** and was excluded from a prior fix request. Release proof requires vendor sandbox contract tests.
- **CI:** `.github/workflows/ci.yml` declares checks, but this review did not obtain an exact-SHA remote run. A local passing unit suite does not establish integration, dependency-audit, or image-build success.
- **Review method:** inspected application routes, services, repositories, models, migrations, workers, configuration, Docker/Compose, tests, and prior review. No new confirmed N+1 defect was found; this is not a guarantee for unmeasured list paths.
